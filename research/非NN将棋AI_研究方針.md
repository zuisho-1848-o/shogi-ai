## 1. 前提の整理（ここを外すと時間を溶かす）

### 1.1 規模感
- 将棋の局面数は約 10^68〜10^71、ゲーム木は約 10^226。全局面を列挙して解く方法は、計算資源をどれだけ使っても届かない。
- **9×9を n×n に一般化した将棋は EXPTIME完全**（Adachi–Kamekawa–Iwata 1987）。つまり「うまい表現さえ見つければ一般に多項式時間で解ける」という望みは、一般化した将棋では理論的に否定されている。
  - ただし 9×9 に固定すれば問題の大きさは定数なので、この結果は「平手局面に短い証明はない」とは言っていない。**狙うべきは、実戦に出てくる局面に偏った構造**（玉の囲い、詰みの形、手筋）。

### 1.2 「NNを使わない」と「計算資源をほぼ使わない」は別の問題
- NNUE は浅いネットワークで、CPUだけでスマホでも動く。**目標②の「GPUなし」は、NNUEでもう満たされている。**
- NNでない評価関数（Bonanza 系の3駒関係＝KPPT。中身は線形モデル）でも、2017年ごろの時点でトップ棋士を大きく上回っていた。手元の `engines/yaneuraou/YaneuraOu_KPPT-*` がまさにそれ。
- つまり目標②を非NNでやる場合の論点は「強さ」より、**評価関数ファイルの大きさ（KPPTはおよそGB級、NNUEは64MB）と計算速度**。これは数学的に圧縮する題材になる（A5）。

### 1.3 目標①について正直に
- 最強のNNエンジンも最善手を指し続けているわけではない。強くする余地はある。
- 非NNがNNを超える筋は、ほぼ次の2つに限られる。
  1. **計算を前もって済ませておく（償却）**: 一度証明した事実（定理・データベース）は、何度でもタダで使える。NNは毎回近似を計算し直している。
  2. **正確さ**: 近似ではなく、証明済みの結論で枝を切る。間違えないので、深く読んでも破綻しない。
- この2つが一番効くのは**終盤（詰み・必至・入玉）**。中盤の大局観でNNに勝つのは最難関で、そこは後回しにする。

## 3. 推し案の詳細

### 3.1 C2：証明の一般化による定理ライブラリ（目標①の柱）

**アイデア**: df-pn が「この局面は詰む」と証明したとき、その証明木を最後まで実行するのに必要だった情報は盤面の一部だけ。

```
証明木 → 各ノードで「どの駒の利き・どのマスが空いていること・どの持ち駒」に頼ったかを記録
       → その条件を全部合わせたもの = 「この条件を満たす局面は全部詰む」という定理（パターン）
```

- 守り方の応手を網羅するには、「守り方の駒がそこに無いこと」も条件に入る。これを含めないと定理は正しくならない（ここが一番難しいところ）。
- 持ち駒は単調性を使う。**攻め方の持ち駒が増えても詰みは崩れない**（攻め方は増えた駒を使わなければよいので、これは証明できる）。玉方の持ち駒が減る場合も同様。だから定理の条件は「持ち駒 ⊇ 〇〇」の形で書ける。
- 定理が貯まると、探索中に**表を引くだけで詰み・必至が分かる**。NNUEエンジンの詰み探索より深い終盤を、ほぼ計算なしで判定できる可能性がある。
- 既存研究の近い例: 囲碁の安全性証明、将棋の詰みパターン学習など。まず重複調査をする。

**最小実験**: 3〜7手詰めを1万問解く → 定理を抽出 → 別の1万問で「表を引くだけで解ける割合」と「誤判定0件」を測る。

### 3.2 B4/B5：脅威空間探索・λ探索（目標①②をつなぐ）

- 将棋の終盤は「詰めろ（次に詰む状態）をかけ続けて、相手が受けきれるか」の戦い。λ探索はこの構造をそのまま形にした手法。
- λ2（詰めろ）の空間で勝ちを証明できれば、それは必至の発見になる。通常のαβ探索は、深さ不足で必至を見落とすことがある。
- 中盤以降の通常探索の中で、**λ探索が証明できた枝だけ評価値を確定値に置き換える**。これで「間違えない終盤」を作れる。

### 3.3 A5：KPPTの低ランク分解（目標②）

- KPP テーブル `W[k][p1][p2]` を `Σ_r a_r[k] ⊗ b_r[p1] ⊗ b_r[p2]` のように分解する。ランク r を調整すれば、大きさと精度のトレードオフを測れる。
- 差分計算（1手指すたびに変わった部分だけ計算し直す）がそのまま使えるので、速度も落ちにくい。
- 成果指標: 「r = ?, ファイル ?MB で、元のKPPTとの勝率差 ±?」。スマホで動くかはファイルの大きさ（目安100MB未満）とノード毎秒で判断する。

### 3.4 D1'：ZDDで集合ごとに後退解析（目標③の柱）

- 1局面ずつのDFS（archive Phase 1 は Python で約1.2万ノード/秒）とは発想を変える。
  - 「詰んでいる局面の集合」→「1手で詰みの集合に入れる局面の集合」…と、**集合同士の演算**で後退解析する。
- 練習台の順番: どうぶつしょうぎ（解決済み＝正解と照合できる）→ 4×4前後の自作ルール → 既存の小さい将棋（5五将棋など。解決状況は要調査）。
- 失敗しやすい点: 打ち駒で集合の構造が崩れ、決定図が爆発すること。**爆発の仕方を測ること自体**が研究成果になる。

### 3.5 D2：Lean4の証明書チェッカー

- 探索エンジンは「証明書」（証明木。必要なら圧縮して）を出力するだけにし、それが正しいかは小さくて信頼できるチェッカーが検査する。
- まず「詰み証明木の検証」から始め、ルール（打ち歩詰め・連続王手の千日手）の形式化は段階的に進める。
- C2 の定理も Lean で検証できれば、「機械が発見し、機械が検証した将棋の定理集」になる。人にも見せられる成果。

## 5. 最初に作る基盤（全案で共通）

1. **速い盤面ライブラリ**: python-shogi は遅い（archive の実測で約1.2万ノード/秒）。
   - 選択肢: (a) `cshogi`（C++製・Pythonから使える）を入れる【最小コスト】 / (b) Rust で自作のビットボード【独自探索を深くやるなら必要】。
   - おすすめ: **まず (a) で実験を回し、遅さがボトルネックになった案だけ (b) で作り直す。**
2. **対局リーグ**: USI で自作エンジンとやねうら王（Material / KPPT / NNUE）を総当たりで対局させ、Elo を出す。同ノード数と同時間の2条件で比べる。
3. **問題セット**: 詰将棋（手数ごと）、必至問題、実戦の終盤局面（`kifu/` の自分の棋譜からも取る）。
4. **証明書の形式**: 証明木のシリアライズ形式を最初に決める（C2 と D2 の両方が使う）。

ディレクトリ案: `research/`（メモ）、`lab/`（実験コード。kifu_review とは分ける）。

## 6. リスクと割り切り

- **中盤の強さでNNUEに勝つ**のは、どの案でも保証がない。終盤で勝つ → 範囲を広げる、の順にする。
- 「NNを使わない」の線引き: 線形・多重線形・決定木・論理規則はOK、多層の非線形関数近似はNG、とする。NNUEは比較相手と教師データの生成にだけ使う（A2で教師にするのは「NNに頼る」グレーゾーンなので、使ったことを明記する）。
- 独創性の主張は、すべて**先行研究を調査する前の仮説**。特に C2・D1'・A5 は着手前に論文を調べる（IPSJ のゲーム情報学研究会、ICGA Journal、Computers and Games）。
- メモリ16GB: ZDD・DB系は外部記憶（SSD）を使う設計が必要になる可能性が高い。
